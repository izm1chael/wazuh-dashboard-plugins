# Threat intelligence catalog and indicator exchange

Status: experimental development candidate; no production qualification. Requires matching dashboard and indexer builds with experimental incidents enabled.

## Delivered functionality

- A dedicated Threat intelligence workspace with a shared indicator catalog, state and text filters, immutable local identities, source labels, optional external STIX indicator IDs, explicit confidence (0–100), TLP handling label, validity interval and authenticated creation attribution.
- Supported types: canonical IPv4 literal, ASCII DNS domain, MD5, SHA-1, SHA-256. Domains and hashes are normalized to lowercase; historical hunts remain exact source-field searches. No CIDR, IPv6, URL, complex STIX pattern or reputation verdict. UTC millisecond precision; positive validity up to 366 days; already expired imports are rejected. States are computed at catalog read: pending, active, expired, revoked. Terminal revocation is attributed and retains original fields; an expired or revoked indicator may be renewed as a new record. An external STIX ID cannot be reused, including for a new STIX object version.
- Atomic add (1–20 entries), revoke, record external sighting, withdraw external sighting. The entire bounded catalog changes in a single optimistic-concurrency write. Initial document creation is create-only, later mutations use seq_no/primary_term CAS and expected catalog revision. No retry on an ambiguous result. Record attribution is server derived, not caller supplied. Catalog validation checks every revision is represented by a creation batch or an attributed revocation/sighting/withdrawal.
- External sighting attestations record source label, observed UTC time, reported count, authenticated analyst and recorded time; must be within elapsed indicator validity, not later than revocation. Withdrawal preserves the original attestation and records actor/time/reason. Same source/time active duplicate is rejected. These are shared analyst attestations of external reports, not verified Wazuh findings or automatically generated sighting receipts. No raw source or automatic copy of hunt output. Do not enter restricted telemetry, secrets or sensitive URLs.
- Historical match: prepare a single indicator or 1–20 active indicators of the same type from the filtered view. Prepopulate an elapsed validity interval or the common interval up to the preceding 24 hours. Analysts explicitly run or edit the existing bounded exact hunt. Queries require the hunt grant and caller's existing finding search permissions; no implicit elevation, no automatic query, no stored telemetry results, no automated classification or response.
- Local STIX 2.1 subset: paste a bundle of 1–20 unmarked, non-revoked Indicator objects using supported single equality patterns (IPv4, domain, MD5, SHA-1, SHA-256), explicit confidence and expiry. Reject duplicate JSON keys, arbitrary properties, markings/granular markings, extensions, non-indicators and complex patterns. Preview normalized fields; source/handling label supplied by analyst, default AMBER. Optional descriptive properties are not retained; original external ID is retained, not the original STIX document. The server validates and stores normalized entries, not raw STIX. Local export of selected active CLEAR indicator only, after catalog revision and state recheck; generate a new local-ID-based Indicator and Bundle, without marking definitions, source metadata, sightings or external ID. No external transmission. This is a constrained interchange, not complete STIX 2.1 validation or a TAXII implementation. Reference: https://docs.oasis-open.org/cti/stix/v2.1/os/stix-v2.1-os.html

## Authorization and persistence

Separate cluster grants: cluster:admin/wazuh/incident/indicator_read and cluster:admin/wazuh/incident/indicator_write. Write grants return only revision/changed receipt; read grant is needed to browse. Dashboard uses asCurrentUser; indexer verifies feature gate, action and principal before a fixed internal catalog store. No general backing-index permission. Catalog is single-SOC shared among read-authorized users. TLP is handling metadata, NOT per-record ACL or a guarantee of export control: the local export UI restricts CLEAR, but an authorized reader already sees the catalog. Never use this store for information that must be isolated from its readers. Do not route it to an AI provider.

Hidden strict state index .wazuh-incident-indicators-v1, exact document ID catalog. Disabled-object field stores catalog rows in source rather than indexing every attribute. Separate from existing native Wazuh threatintel enrichment/content indices, which are unchanged. Limits: 200 lifetime indicator rows (including expired/revoked), 20 per add, 10 lifetime attestations per row, 500 total attestations (including withdrawn), 16 KiB mutation payload. No purge/archive, no automatic feed import, no independent tamper-evident audit ledger. Limit behavior is explicit; at capacity a separately reviewed archival design is required. No mixed-version installation support; use final phase heads, not transitional commits.
